Как устроен Tokosint

Tokosint — форк BBOT (рекурсивного движка OSINT) со строгой валидацией каждой находки и каждой связи между находками. BBOT отвечает на вопрос «что можно найти от этой цели»; Tokosint добавляет «существует ли это сейчас, действительно ли это цели и откуда мы это знаем». Только пассивные источники: к цели напрямую ничего не обращается, кроме DNS-резолва через публичные резолверы.

1. Рекурсивный движок

Всё — это события: имя хоста, IP, порт, технология, email. Скан начинается с затравок (цели) и пропускает каждое событие через один конвейер. Каждый модуль следит за своими типами событий и порождает новые, которые возвращаются в начало того же конвейера: поддомен, найденный одним источником, резолвится, классифицируется, валидируется и затем уходит во все остальные источники, которым нужны поддомены. Рекурсия останавливается сама: уже виденное событие отбрасывается (дедупликация), а слишком далёкое от цели не отдаётся модулям (дистанция скоупа).

Модули перехвата видят каждое событие раньше остальных и в фиксированном порядке; модуль перехвата в состоянии ошибки остановил бы весь конвейер, поэтому они маленькие и не падают на плохом конфиге. Вывод, ложные находки и статистика запросов по источникам (module_stats.json) пишутся в scans/<скан>/.

2. Дистанция скоупа

У каждого события есть дистанция от цели: 0 — цель и её поддомены (и домены, поднятые в скоуп, см. связанные домены), 1 — один шаг (IP, в который резолвится имя из скоупа, DNS- или почтовый провайдер цели), 2+ — дальше.

search distance определяет, с какими событиями могут работать модули (источники ищут по именам из скоупа; модулям, которым нужны IP имён из скоупа, разрешён один лишний шаг); report distance — что попадёт в вывод. Сама по себе дистанция ничего не говорит о том, чья это находка, — для этого и нужна валидация.

3. Модули и типы событий

Каждый модуль делает одно дело: запрашивает один API, резолвит, классифицирует. Он объявляет, какие типы событий потребляет и какие порождает, а движок связывает модули между собой. Наведите на модуль или тип события, чтобы увидеть его связи: порождает / потребляет.

Каждый модуль-источник объявляет и meta.freshness — current (источник видит интернет сейчас: DNS, живые сканеры), historical (архивы, пассивный DNS, логи сертификатов) или inherit (производное от родителя: IP порта). С этого начинается правило статуса ниже.

4. Статус находки

Каждая находка — валидная (существует сейчас), историческая (существовала, сейчас не подтверждена) или ложная (не настоящая или не цели). Статус считается вдоль пути обнаружения:

статус = min(актуальность источника, статус родителя)  ·  проверка verified поднимает до валидного

Потомок не может быть актуальнее родителя, если его ничто не подтверждает сейчас: IP из архивной записи мёртвого имени остаётся историческим. Ложные находки убираются из скана (модули с ними не работают) и сохраняются с причиной в validity_false.jsonl; их потомки тоже ложные.

5. Проверки валидации

Выполняет validity для каждого события по уже известным данным (DNS-записи, теги) — без обращения к цели. Побеждает самый сильный вердикт: ложное > несвязанное > историческое > verified.

6. Чьё это: третьи стороны и владелец IP

third-party (третья сторона): связь настоящая («цель этим пользуется»), но это не актив цели — почтовые и DNS-провайдеры цели (имена из её MX/NS/TXT), прокси-фронты и то, что на них найдено. Показывается как валидное с пометкой третья сторона, фильтруется во вкладке «Анализ».

7. Связанные домены

Второй бренд или дочерняя компания живут на другом домене. related_domains собирает DNS-доказательства для каждого домена вне скоупа, замеченного рядом с целью, и поднимает его в скоуп только при наличии обратной ссылки — собственные записи кандидата указывают на цель (провайдер никогда не направляет свои записи на клиента):

Для подъёма в скоуп нужны обратная ссылка и сумма баллов ≥ 4. Всё, что найдено через поднятый домен, помечено в «Анализе» как через subsidiary.example (фильтр «через связанные домены»), чтобы активы дочерней компании не смешивались с активами самой цели.

8. Одна находка — много путей

Находка часто приходит несколькими путями: сначала из архива, позже из живого источника. Веб пересчитывает статус по всему графу наблюдений: статус(находки) = максимум по путям статуса пути — побеждает лучшее доказательство. Карточка актива показывает все пути графом («Показать цепочку обнаружения»). Аналитик может задать статус вручную; вычисленный хранится рядом, а каждое изменение записывается в журнал (status_overrides) для улучшения правил.

9. Даты, запросы и квоты

Последнее наблюдение — дата, которую сообщает сам источник (time_last пассивного DNS, lastupdatetime FOFA, время баннера Shodan, даты OTX / LeakIX / Netlas); пусто, если источник даты не даёт. Дата скана — когда шёл скан. Каждый API-запрос каждого источника учитывается вместе с исходом (ok, рейтлимит, квота, авторизация, недоступен), а квота аккаунта читается до и после скана — в отчёте скана видно, что упало и сколько потрачено.
