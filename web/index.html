How Tokosint works

        
Tokosint is a fork of BBOT (an OSINT recursion engine) with strict validation of every finding and of every
        relation between findings. BBOT answers "what can be found from this target"; Tokosint adds "is it real now,
        is it really the target's, and how do we know". Passive sources only: nothing here touches the target directly,
        except DNS resolution through public resolvers.

      


      

        
1. The recursive engine

        
Everything is an event: a hostname, an IP, a port, a technology, an email. A scan starts from seeds
        (the target) and pushes every event through one pipeline. Each module watches some event types and emits new
        events, which go back to the start of the same pipeline - so a subdomain found by one source is resolved, classified,
        validated and then handed to every other source that wants subdomains. Recursion stops on its own: an event that was
        already seen is dropped (dedup), and an event too far from the target is not handed to modules (scope distance).

        
        
Intercept modules see every event before anyone else and in a fixed order; an intercept module in error
        state would stop the whole pipeline, so they are kept small and never fail on bad config. Output, false findings and
        per-source request statistics (module_stats.json) are written to scans/<scan>/.

      


      

        
2. Scope distance

        

          
          

            
Every event carries its distance from the target: 0 - the target and its subdomains (and domains promoted into
            scope, see related domains), 1 - one hop away (an IP an in-scope name resolves to,
            the target's DNS or mail provider), 2+ - further.

            
search distance decides which events modules may work on (sources look up in-scope names; modules that need
            IPs of in-scope names accept one extra hop); report distance decides what reaches the output. Distance alone
            says nothing about whose a finding is - that is what validation is for.

          

        

      


      

        
3. Modules and event types

        
Each module does one thing: query one API, resolve, classify. It declares the event types it consumes and
        produces; the engine wires them together. Hover a module or an event type to see its links:
        produces / consumes.
        

        

        
Every source module also declares meta.freshness - current (the source sees the internet
        now: DNS, live scanners), historical (archives, passive DNS, certificate logs) or inherit (derived from the
        parent: an IP of a port). It is the start of the status rule below.

      


      

        
4. Status of a finding

        
Every finding is valid (exists now), historical
        (existed, not confirmed now) or false (not real or not the target's). The status is
        computed along the discovery path:

        
status = min(freshness of the source, status of the parent)  ·  a verified check lifts it to valid

        
        
A child can never be fresher than its parent unless something confirms it now: an IP found in an archive
        record of a dead name stays historical. False findings are removed from the scan (modules never work on them) and kept
        with the reason in validity_false.jsonl; their descendants are false too.

      


      

        
5. Validation checks

        
Run by validity on every event, from what is already known (DNS records, tags) - never by contacting the target.
        The strongest verdict wins: false > unrelated > historical > verified.

6. Whose is it: third parties and IP ownership

        
        
third-party: the relation is real ("the target uses it") but it is not a target asset - the target's mail and DNS
        providers (names from its MX/NS/TXT records), proxy fronts, and what is found on them. Shown as valid, marked
        third party, filterable in Analysis.

      


      

        
7. Related domains

        
A second brand or a subsidiary lives on another domain. related_domains collects DNS evidence for every
        out-of-scope domain seen next to the target and promotes it into scope only with a backref - the candidate's own
        records point at the target (a provider never points its records at a customer):

        
        
Promotion needs a backref and a score ≥ 4. Everything found through the promoted domain is marked
        via subsidiary.example in Analysis (filter "via related domains"), so the subsidiary's assets are not mixed with
        the target's own.

      


      

        
8. One finding, many paths

        
A finding often arrives several ways: first from an archive, later from a live source. The web view recomputes the
        status over the whole graph of observations: status(finding) = max over paths of the path status,
        so the best evidence wins. The asset card shows every path as a graph (Show discovery chain).
        An analyst can set a status by hand; the computed one is kept next to it and every change is logged
        (status_overrides) to improve the rules.

      


      

        
9. Dates, requests and quotas

        
Last seen is the date the source itself reports (passive DNS time_last, FOFA lastupdatetime,
        a Shodan banner timestamp, OTX / LeakIX / Netlas dates); empty when the source gives no date. Scan date is when
        the scan ran. Every API request of every source is counted with its outcome (ok, rate limit, quota, auth, unavailable)
        and the account quota is read before and after a scan - the scan report shows what failed and what was spent.

Enrich 

  

    
Runs the chosen sources over the findings this scan already has, in the same scope (its targets and
    the domains promoted into scope). Valid and historical findings of the types the sources take are the seeds; third-party
    and false ones are not. A historical finding stays historical, and so does what a source finds on it. The result is a
    separate scan shown together with this one; a company scan feeds the company's timeline.
